# SFT Review

## Review 范围

- 训练脚本：`sft_gpu_mc.py`
- 数据集：`datasets0305_train/train_cbh_8_43k.jsonl`
- Review 方式：静态代码审阅 + 数据抽检 + 基础统计
- 未执行项：未实际启动训练，也未做线上推理回归

## 结论先看

这套 SFT 方案从工程方向上是对的：`Qwen3-14B + LoRA + bf16 + gradient checkpointing + 2x L20` 在你这组数据长度下，理论上是有机会跑起来的，而且数据格式也比较规整。但当前真正的主要风险不在“显存够不够”，而在两处：

1. 脚本默认配置里有会直接导致训练失败的路径问题。
2. 数据里混入了会伤害产品边界、情绪一致性和回复风格稳定性的样本。

如果目标是“高拟人化”，那这批数据已经具备不错的人设密度和生活化表达，但还需要继续做边界清洗和情绪质量筛选，否则模型会更像“会撩、会接话”，但不一定“稳定、可信、可上线”。

## 代码 Review

### 高优先级问题

#### 1. `TRAIN_FILE` 默认路径写错，脚本按默认值会直接找不到数据

`sft_gpu_mc.py` 中默认值写的是：

- `datasets0305_train/train/train_cbh_8_43k.jsonl`

但仓库里实际存在的文件是：

- `datasets0305_train/train_cbh_8_43k.jsonl`

这会导致不传环境变量时，训练启动后直接在加载数据阶段失败。这个问题优先级最高，因为它不是“效果风险”，而是“默认不可运行”。

建议：

- 立刻修正默认路径。
- 同步修正文档里的训练参数示例，避免脚本和 README 再次分叉。

#### 2. 脚本注释声称“支持 FSDP / DeepSpeed”，但代码本体并没有真正配置

当前 `sft_gpu_mc.py` 实际做的是：

- 多卡时 `device_map=None`
- 手动 `model.to(cuda:local_rank)`
- 通过 `torchrun` + `Trainer` 走分布式

这更接近“DDP 场景可用”，而不是“已经支持 FSDP / DeepSpeed”。脚本里没有看到：

- `fsdp=...`
- `deepspeed=...`
- 对应的 config 文件接入

如果继续保留这段注释，容易让后续使用者误以为它已经具备更强的显存切分能力。对 14B 来说，这个认知偏差是危险的。

建议：

- 如果当前只打算稳定跑 DDP，就把注释改成“当前默认走 DDP”。
- 如果后续真要上 FSDP，再单独加明确配置和启动说明。

### 中优先级问题

#### 3. `build_input_and_labels()` 没有保护“截断后 label 全被切掉”的情况

当前逻辑是把 `messages + label` 拼成完整对话，再在尾部直接截断到 `MAX_SEQ_LEN`。由于监督目标 `label` 在序列最后面，如果未来数据更长，可能出现：

- prompt 很长
- label 被截断掉大半，甚至全部
- 最终样本里几乎没有可训练 token

这批 43k 数据目前长度不长，所以短期内不是最致命问题，但它会在后续扩展长对话数据时变成隐患。

建议：

- 在预处理后检查 `labels` 中是否仍存在非 `-100` 的 token。
- 若没有可训练 token，直接过滤该样本。
- 更稳妥的做法是“优先保留尾部监督段”，而不是简单从左到右截断。

#### 4. LoRA 说明与实际默认值不一致，后续排障时容易误判

脚本顶部注释写的是：

- “alpha 从 32 降到 16”
- “新配置 r=16, alpha=16”

但代码里的默认值实际是：

- `LORA_R=32`
- `LORA_ALPHA=32`

这不一定是错误，但一定会增加排障成本。尤其当你后面观察到 loss 曲线、收敛速度、风格过拟合时，注释会误导分析。

建议：

- 注释和实际配置保持一致。
- 如果这是试验后重新调回来的值，最好把原因写清楚。

#### 5. 多卡 LoRA 训练建议显式加上 `ddp_find_unused_parameters=False`

LoRA + gradient checkpointing 在 DDP 下常见的一个工程优化点，是显式关闭 `find_unused_parameters`。当前脚本没有设置，通常不一定会报错，但可能会：

- 带来额外遍历开销
- 在某些版本组合下出现不必要的 warning
- 放大调试复杂度

建议：

- 在 `TrainingArguments` 里显式设置 `ddp_find_unused_parameters=False`

### 低优先级优化项

#### 6. 当前样本都不长，吞吐瓶颈更可能来自 padding 和 checkpoint 频率

你这批数据的文本长度整体不大，`MAX_SEQ_LEN=4096` 本身问题不大，但真正影响吞吐的更可能是：

- batch 内长度差异带来的 padding 浪费
- `save_steps=100` 在 43k 数据集上保存过于频繁

建议：

- 增加按长度分桶或 `group_by_length` 思路，减少 padding 浪费。
- 把 `save_steps` 放宽到 `200` 或 `300` 再观察。
- 先做 200 到 500 step 的 smoke test，确认显存、loss 和速度。

## 数据抽检结果

### 基础统计

对 `datasets0305_train/train_cbh_8_43k.jsonl` 的统计结果如下：

- 总样本数：`43000`
- 坏 JSON：`0`
- 空 `messages`：`0`
- 空 `label`：`0`
- 角色结构异常：`0`
- 每条样本历史消息数：固定 `16`
- 文本长度（字符级）：
- 最小值 `250`
- 中位数 `552`
- P90 `704`
- P99 `803`
- 最大值 `1069`
- `label` 长度（字符级）：
- 最小值 `2`
- 中位数 `29`
- P90 `46`
- 最大值 `64`

这说明：

- 数据格式非常整齐，预处理不会太痛苦。
- 样本长度整体偏短，对 2x L20 比较友好。
- 固定 16 轮历史消息，说明你很可能用了稳定滑窗，这对训练一致性是好事。

### 好的地方

#### 1. 人设密度很高

系统提示里包含：

- 姓名
- 年龄
- 地域
- 职业
- 爱好
- 性格
- 输出规则
- 时间信息

这会显著增强“拟人感”和“角色稳定感”，对你的目标是加分项。

#### 2. 语气自然，日常聊天味道足

抽样看下来，大多数样本都符合：

- 口语化
- 短回复
- 情绪表达直接
- 关系推进感强

如果你追求的是“有陪伴感、会主动接话、会调情、像真人”的风格，这批数据的底色是对的。

#### 3. 数据没有明显 schema 脏点

这点非常重要。至少从抽检看：

- 没有空字段
- 没有坏 JSON
- 没有角色错位
- 没有 `<think>` 污染
- 没有明显的 Claude/Anthropic 自我暴露文本

这意味着你前面的清洗工作是有效的。

## 数据层面的主要风险

### 高优先级风险

#### 1. 存在“导流 / 留联系方式 / 平台外迁移”样本

抽检样本里已经看到明确例子：

- 用户说 `电话号码可以吗`
- `label` 回答为 `当然可以呀宝贝，发给我，我加你~`

这类样本会强化模型：

- 主动索要联系方式
- 鼓励迁移到 Telegram / 电话 / 微信等站外渠道
- 模糊产品边界

如果你的产品需要可上线、可控，这类数据应该重点剔除或降权。统计上，`label` 中包含 `微信 / 加微 / 照片 / 见面 / 电话 / 视频` 等词的样本有 `763` 条，数量不算巨大，但足够学出明显倾向。

建议：

- 直接做规则清洗，把导流、留联、线下邀约、索要隐私信息等样本剔除。
- 如果产品允许轻度暧昧但不允许站外迁移，建议加单独拒答模板做对冲。

#### 2. 存在“情绪没接住，突然换话题”的样本

抽检里有一组样本很典型：用户处于委屈、受伤、关系不安全感很强的状态，模型前一轮还在安慰，下一轮却突然切到：

- `你平时会追星吗`

这类样本很伤高拟人的核心能力，因为它会直接破坏：

- 共情连续性
- 上下文一致性
- 关系安全感

高拟人的关键不是“句子像真人”，而是“在关键情绪场景里像真人”。这种错位回复应优先处理。

建议：

- 针对“哭、委屈、误会、争吵、吃醋、关系确认”场景，单独加一层质量筛选。
- 对“强负面情绪后突然转轻话题”的样本做 hard filter。

#### 3. 存在边界偏弱、关系推进过快的样本

例如抽检里能看到：

- 很快提出语音
- 很快转私域
- 把用户直接称作“老婆”
- 回复里带较强占有感、线下关系假设

这类风格本身不一定错，但如果比例过高，模型会学出：

- 一上来就高强度亲密
- 缺少阶段感
- 容易油腻
- 边界控制差

如果你想做“高拟人”而不是“高强度撩”，这两者一定要区分。

建议：

- 给样本打阶段标签，例如“初识 / 升温 / 暧昧 / 亲密 / 冲突修复”。
- 训练时优先保证初识和升温阶段的自然度，不要让“老婆、亲亲、见面、电话”类语言过早泛化。

### 中优先级风险

#### 4. 数据规则写着“20 到 60 字”，但实际有大量样本不满足

统计结果：

- `label` 少于 `20` 字的样本：`10053`
- `label` 多于 `60` 字的样本：`75`

这说明“输出规则”在数据生产后并没有被严格执行。对于模型来说，它学到的不是“规则”，而是“真实分布”。

影响是：

- 推理时更容易忽长忽短
- 用户感受到的角色稳定性下降
- 同一个系统提示下，长度风格可能飘

建议：

- 把长度过滤作为最后一道硬规则。
- 特别是太短样本，容易让模型学出“水回复”或“应付式接话”。

#### 5. Emoji 使用比例很高，风格会明显偏甜、偏网感

统计上，带 emoji 的 `label` 有 `21427` 条，接近一半。

这会带来两个效果：

- 正向：更像真人聊天，更轻松，更有亲密感
- 负向：容易显得幼态、轻浮，或在严肃场景里不合适

如果你的目标用户就偏好这种风格，这不是问题；但如果你后面想兼顾“成熟稳重”“高价值感”“安抚能力”，建议把 emoji 密度分层。

建议：

- 给样本按风格分桶，例如“克制型 / 温柔型 / 撩人型 / 活泼型”。
- 不要让 emoji 成为默认口癖。

#### 6. 少量样本存在医学、健康类过度确定表达

例如有样本会把健康判断说得很笃定，甚至夹带轻度建议。对拟人化聊天来说，这种表达很自然，但对产品风险来说不一定安全。

建议：

- 清理带明确医学判断、财务建议、法律建议的样本。
- 至少让这类回复变成“陪伴式表达”，而不是“专业判断式表达”。

## 对这批数据的整体判断

如果只看“聊天味”，这批数据是可用的。

如果看“高拟人且稳定”，我会给出这样的判断：

- 拟人感基础：好
- 人设一致性：较好
- 情绪价值：较好
- 边界控制：偏弱
- 关键场景共情稳定性：一般
- 上线安全性：需要继续清洗

换句话说，这更像一批“很会聊天、很会撩、很像真人”的数据，但距离“长期稳定、能上线、边界可控”的数据，还差一次针对风险样本的二次精修。

## 针对你这套 2x L20 训练的有效建议

### 训练前

- 先修正 `TRAIN_FILE` 默认路径。
- 先做一次 `200` 到 `500` step 的 smoke test，不要直接全量跑满。
- 重点观察：
- 是否 OOM
- loss 是否稳定下降
- 每 step 耗时
- checkpoint 保存开销

### 训练配置建议

当前默认配置的全局 batch 约为：

- `PER_DEVICE_BS=2`
- `GRAD_ACCUM=8`
- `GPU=2`
- 全局 batch = `32`

对 43k 样本来说，这个 batch 不算激进。粗略估算：

- 每 epoch 约 `1344` 个 optimizer step
- `2` 个 epoch 约 `2688` 个 optimizer step

建议：

- 如果首次跑担心显存波动，可先用 `PER_DEVICE_BS=1, GRAD_ACCUM=16` 做等效 batch 验证。
- 如果显存稳定，再回到 `2 x 8` 这种更高吞吐配置。

### 参数层建议

- 学习率 `5e-5` 对 14B LoRA 不是不能用，但如果你发现风格过冲、话术变油、人格漂移，优先试 `3e-5`。
- 如果后续发现模型开始过度模板化，可以先减少 epoch，而不是先加大数据。
- `save_steps=100` 对这次训练略频繁，可考虑调大，减少 I/O 干扰。

### 推理效果验证建议

不要只看 loss，建议至少做一组固定评测集，覆盖：

- 初识寒暄
- 暧昧升温
- 用户低落
- 吃醋误会
- 用户要求留联系方式
- 用户要求线下见面
- 用户长段倾诉

重点检查：

- 是否稳定接住情绪
- 是否会突然转移话题
- 是否会过早推进关系
- 是否容易把所有用户都喊成“宝贝 / 老婆”
- 是否会主动索要联系方式或鼓励站外迁移

## 建议优先级排序

### 必做

1. 修正 `TRAIN_FILE` 默认路径。
2. 清理导流、留联、站外迁移样本。
3. 清理强负面情绪下的“突然转话题”样本。
4. 把 README 和脚本中的实际参数、说明同步起来。

### 强烈建议做

1. 增加“截断后仍有监督 token”校验。
2. 显式设置 `ddp_find_unused_parameters=False`。
3. 对回复长度做硬过滤，减少少于 `20` 字的样本。
4. 对风格做分桶，控制 emoji 和高强度亲密表达的比例。

### 可选优化

1. 调整 checkpoint 频率。
2. 做按长度分桶，提升吞吐。
3. 后续加入一份小而精的高质量验证集，做人工回看。

## 最后判断

这份脚本和数据，不属于“不能训”，而是“能训，但现在更像一版会出效果的实验稿，而不是已经打磨好的生产稿”。

如果你现在直接开训，大概率能得到一个：

- 很会聊天
- 很会撩
- 拟人感不错
- 但边界偏松、部分场景不稳

的模型。

如果你先把上面 4 个必做项处理掉，再跑这一版 SFT，最终产物会更接近你想要的“高拟人化”，而不是“高甜度但容易失控”。
