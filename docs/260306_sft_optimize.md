# 面向逻辑一致性的 SFT 优化方案

> 目标问题  
> 对应 `docs/260306_model_logic_deep.md` 中 `7.1` 的讨论：当前训练样本采用“固定 16 轮历史 + 只监督最后一个短 label”的方式，模型更容易学会“接最后一句”，而不是学会“维护跨轮状态与局部逻辑”。

---

## 一、结论先说

如果只针对 `7.1` 这一点来回答：

> **有，而且不止一种。**

当前 `sft_gpu_mc.py` 的方式，本质上是：

- 给模型一长段历史
- 只让它学最后一轮 assistant 回复
- 这条回复通常又比较短

这种训练对“最后一句怎么接”很有效，但对下面这些能力不够友好：

- 时间状态维护
- 计划/约定持续一致
- 用户意图优先级判断
- 多轮记忆调用
- 减少“顺口但不对”的模板化回复

所以更好的 SFT 思路，不是单纯“再多喂一些类似数据”，而是要调整：

1. **样本切法**
2. **监督目标**
3. **历史保留策略**
4. **训练样本分布**

---

## 二、当前方案的问题到底在哪

结合 `sft_gpu_mc.py`，你现在的监督方式是：

- `messages` 作为上下文
- `label` 作为最后一轮目标
- loss 只打在最后一个 assistant 回复上

这个方案的问题，不是“错”，而是它天然会把模型推向下面这个方向：

```text
给我一段历史
-> 我重点看最后一个 user 在说什么
-> 我学一个像样的短回复
```

于是它比较容易学会：

- 收尾语气
- 互动尾巴
- 局部接话模板
- 风格一致性

但不容易学会：

```text
这段历史里哪些信息是必须跨轮保持的
哪些信息只是背景噪音
刚刚确认过的状态能不能被后一句推翻
```

尤其当：

- 历史轮数固定
- label 很短
- system 很重
- persona/time 字段很多

模型就更容易形成一种局部策略：

> 只要最后一句像聊天，我就优先给一个自然、亲密、会互动的回答。

这正是你现在遇到逻辑跳脱的根本土壤。

---

## 三、比“固定 16 轮 + 最后短 label”更好的 SFT 思路

下面按推荐强度排序。

## 3.1 方案 A：多目标 assistant-turn SFT

这是我最推荐的 SFT 方向。

### 核心思想

不要只监督最后一个 `label`，而是让一个样本中出现的多个 assistant 回合都参与监督。

也就是从：

```text
messages(很多轮) + 最后1个label
```

改成：

```text
完整多轮对话
对其中多个 assistant turn 同时算 loss
```

### 为什么这比当前方案更好

因为它训练的就不再是：

```text
最后一句怎么接
```

而更接近：

```text
这个角色在一段连续对话里，如何持续地说对话
```

这对下面几类能力帮助很大：

- 同一个状态连续保持
- 同一条计划前后不打架
- 人设不乱漂
- 对话节奏更稳定
- 减少“只有最后一句学得很像”的问题

### 举例

当前做法：

```json
{
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "今天周几啊"},
    {"role": "assistant", "content": "今天周五呀"},
    {"role": "user", "content": "睡过头了"}
  ],
  "label": "那你这觉睡得挺实，先起来喝口水清醒一下"
}
```

更好的做法可以变成：

```json
{
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "今天周几啊"},
    {"role": "assistant", "content": "今天周五呀"},
    {"role": "user", "content": "睡过头了"},
    {"role": "assistant", "content": "那你这觉睡得挺实，先起来喝口水清醒一下"},
    {"role": "user", "content": "我还没吃早餐"},
    {"role": "assistant", "content": "那先随便垫点东西，别空着肚子晃"}
  ]
}
```

训练时：

- user 部分 mask
- 所有 assistant turn 打 loss

### 推荐实现方式

你不一定要一步切到“全 assistant turn 全监督”，可以先做折中：

1. 一个样本中保留完整多轮消息
2. 只对最后 `2~4` 个 assistant turn 算 loss
3. 更早的 assistant turn 仍然作为上下文

这样可以兼顾：

- 多轮一致性
- 显存可控
- 实现不复杂

### 优先级

这是 **SFT 侧最值得先试的结构优化**。

---

## 3.2 方案 B：变长窗口，不再固定 16 轮

### 核心思想

不要所有样本都固定 `16` 条历史消息。

改成混合窗口：

- 短窗口：2~4 轮
- 中窗口：6~10 轮
- 长窗口：12~20 轮

按比例混训。

### 为什么有用

固定 16 轮有两个问题：

1. 它会让模型默认把“很多历史”当成常态
2. 但真实需要保持的关键状态，往往并不在所有 16 轮里平均分布

短窗口训练有助于：

- 强化当前意图识别
- 避免过度依赖背景噪音
- 提升对简单事实问答的稳健度

长窗口训练有助于：

- 强化跨轮状态保持
- 训练记忆调用
- 保持计划/时间/情绪连续性

### 推荐比例

一个可执行的起点：

- `40%` 短窗口
- `40%` 中窗口
- `20%` 长窗口

如果当前主要问题是“简单问题都答歪”，可以把短窗口再提高一点。

### 实际意义

这样做会让模型同时学两件事：

- 历史很短时，先准确接住当前意图
- 历史很长时，继续维护状态一致

而不是只在一种固定输入分布下学说话。

---

## 3.3 方案 C：状态锚点优先保留，而不是纯 recency 截断

### 核心思想

当历史太长时，不要简单“只留最近若干轮”。

应该优先保留“状态锚点”消息，比如：

- 当前时间
- 地域/职业/名字
- 已确认的计划
- 用户明确表达过的兴趣点
- 前一轮刚确认过的事实

### 为什么比纯滑窗更好

很多逻辑错误，不是模型完全没看到历史，而是它看到的历史里：

- 真正重要的状态和普通闲聊混在一起
- 模型不知道哪条更重要

所以更好的做法是让数据构造本身帮模型“强调重点”。

### 推荐保留策略

一个实用的窗口构造规则：

1. 永远保留最近 `2~4` 轮
2. 额外保留最近出现的状态锚点 turn
3. 如果还有空间，再按 recency 回填

### 示例

假设对话很长，但里面真正重要的是：

- `今天周五`
- `下午我们去公园`
- `你刚刚说睡过头了`

那么训练样本应优先保留这些 turn，而不是机械保留“最近 16 条”。

### 这对你当前 case 的意义

它能直接改善：

- `周五 -> 周末`
- `说好下午见 -> 晚安`
- `已经说过是悬疑 -> 又问你看什么类型`

这类状态遗失问题。

---

## 3.4 方案 D：从“单步接话”改为“连续续写片段”

### 核心思想

不要只构造“历史 -> 下一句 assistant”。

可以构造：

```text
历史 -> 后续连续 2~3 个 assistant 回合
```

当然 user 轮也在中间出现，但 loss 只打 assistant。

### 为什么有用

因为它训练的不是一句回复，而是一个小的对话轨迹。

这有助于模型学到：

- 刚说完的话，下一轮还要继续自洽
- 不要一轮正常，下一轮就漂
- 不是只会生成“一个像样的句子”，而是会维持一小段连续策略

### 对当前问题的帮助

这对修下面的问题很有效：

- 第一轮先接住了，第二轮又乱反问
- 刚确认状态，下一轮就跳时间
- 第一轮还在共情，下一轮直接采访

### 和方案 A 的关系

方案 A 是“多 assistant-turn 同监督”  
方案 D 是“连续片段训练”

两者可以结合：

- 一条样本里保留连续若干轮
- 对其中多个 assistant turn 同时算 loss

---

## 3.5 方案 E：构造“意图优先”样本，而不是只靠原始聊天流

### 核心思想

很多原始聊天数据是自然发生的，但自然发生不代表最适合训练。

对逻辑一致性任务，建议补一类更“教学型”的 SFT 样本：

- 用户问事实 -> assistant 简洁答事实
- 用户表达情绪 + 兴趣 -> assistant 先接情绪
- 用户只问一个点 -> assistant 不展开整包 persona

### 为什么这仍然是 SFT，而不是 DPO

因为你可以直接把“更稳的答案”写成高质量 label 喂进去。

虽然它不能像 DPO 那样显式压 bad case，但它可以显著增加：

- 正确策略的曝光频率
- 正确节奏的稳定性

### 适合补什么类型

建议至少补以下 4 类：

1. 事实问答简洁回答
2. 时间状态一致
3. 情绪优先再展开话题
4. 不空泛贴合关系

这和 `docs/260306_model_logic_deep.md` 里 `9.2`、`9.3` 的思路是连起来的。

---

## 3.6 方案 F：做“标签化 SFT”，把逻辑目标显式写进样本

### 核心思想

在 system 或 sample metadata 里显式增加一些策略标签，让模型知道当前轮优先级。

例如：

- `策略标签：事实问答，先直接回答，不追加反问`
- `策略标签：当前时间状态必须保持为周五`
- `策略标签：先接情绪，再展开兴趣`

### 为什么值得试

当前你的 system 很多，但大多是：

- 人设
- 风格
- 情绪价值

比较少显式写：

- 当前轮到底该怎么答

如果在 SFT 样本中把这种策略写得更结构化，模型会更容易学到“不同场景优先级不同”。

### 风险

这种方式的缺点是：

- 如果线上推理没有类似格式，泛化会打折
- 标签设计太多会增加 system 噪音

所以更适合做轻量版，而不是把 system 写得更重。

### 推荐方式

不要写很长，只加一行短规则：

```text
当前回复策略：优先回答问题本身，不追加无根据反问。
```

或者：

```text
当前回复策略：已确认今天是周五，后续不得切换到周末语境。
```

## 五、如果只改 `sft_gpu_mc.py`，可以怎么落地

如果你想尽量少改工程，只在现有脚本框架上优化，可以这样做。

## 5.1 从“单 label”改成“完整 messages 监督”

当前 `build_input_and_labels()` 是：

- `messages` 不算 loss
- `label` 算 loss

可以改成新格式：

### 格式 A：完整对话

```json
{
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."},
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ]
}
```

训练时：

- 对所有 assistant turn 标注 labels
- 对 user/system 标成 `-100`

### 格式 B：最后 N 个 assistant turn 监督

如果担心风格漂或监督过重，可以折中：

- 更早的 assistant turn 也 mask
- 只放开最后 `N=2~3` 个 assistant turn 的 loss

这会比当前方案更适合逻辑一致性。

## 5.2 截断策略改成“保尾 + 保锚点”

当前如果超长，是直接从头截到 `MAX_SEQ_LEN`。

更好的策略是：

1. 先保证最后监督段完整保留
2. 再保证关键状态锚点保留
3. 最后才裁掉普通历史

否则会出现：

- 监督段保住了
- 但关键状态丢了
- 训练出来还是学“最后一句像什么”

## 5.3 样本打标签，做混合采样

建议给数据加 `sample_type`，比如：

- `fact_qa`
- `time_state`
- `emotion_anchor`
- `memory_recall`
- `normal_chat`

训练时做配比采样，而不是让“普通甜聊”淹没逻辑样本。

一个起步配比可以是：

- `50%` 普通样本
- `20%` 事实问答
- `15%` 时间状态
- `15%` 情绪/记忆 hard case

## 六、是否需要把 SFT 做成 curriculum

我认为值得。

## 6.1 推荐的 curriculum 思路

### 阶段 1：短窗口 + 简单逻辑

训练：

- 事实问答
- 简单时间状态
- 短上下文接话

目标：

- 先把“别乱答”学稳

### 阶段 2：中长窗口 + 连续状态保持

训练：

- 周几/时段/计划
- 用户细节记忆
- 连续 2~3 个 assistant turn 监督

目标：

- 再把“别前后打架”学稳

### 阶段 3：风格融合

最后再混入更多自然陪聊数据，保持：

- 拟人感
- 情绪价值
- 自然口语

目标：

- 避免模型变得太硬、太像客服

### 为什么比一次性混训更好

因为你当前的风险不是“不会说”，而是“会说得太熟练、太顺口、太会接，但不够对”。

先稳逻辑，再回灌风格，会更合理。

## 七、我不太建议的几种做法

## 7.1 继续维持固定 16 轮，只是多加数据

这通常只会让模型：

- 更会接最后一句
- 更会复现高频话术

不太会从根上改善 `7.1` 的问题。

## 7.2 system 写得更重、更长

如果只是继续往 system 塞更多规则，很可能会：

- 增加噪音
- 增加字段冲突
- 让 LoRA 更依赖表层模板

所以与其把 system 堆重，不如把样本结构和监督目标改对。

## 7.3 只靠更长上下文

更长上下文不等于更好的状态维护。

如果监督目标还是只打最后一个短 label，那么：

- 上下文再长
- 模型还是可能只学“最后一句接得像”

所以关键不是长度本身，而是：

> **模型有没有被训练去对多轮状态负责。**

这虽然不如方案 1，但也会比当前方式明显好。

## 九、我对你这个项目的最终建议

结合你现在的问题类型，我最建议的不是“换更长上下文”，而是下面这条：

> **把 SFT 从“最后一句回复训练”升级成“连续对话行为训练”。**

更具体地说：

1. **监督目标**：从只监督最后一个 label，改成监督多个 assistant turn  
2. **样本结构**：从固定 16 轮，改成变长窗口  
3. **历史选择**：从纯 recency，改成“recency + 状态锚点”  
4. **样本分布**：加入足够多的逻辑 hard case SFT  
5. **训练节奏**：先稳逻辑，再混风格

如果只让我选一个最优先动作，我会选：

> **先改成“最后 2~3 个 assistant turn 同时监督”的多目标 SFT。**

因为它最直接地修复了 `7.1` 里那个核心问题：

> 当前模型只被训练去对“最后一句回复”负责，而不是对“这一小段对话的连续一致性”负责。

## 十一、最后总结

针对 `7.1`，更好的 SFT 思路不是“把历史喂得更长”，而是：

- **让监督更连续**
- **让窗口更多样**
- **让状态更显式**
- **让 hard case 占足权重**

你现在这套问题，本质上不是“模型没看到足够多历史”，而是：

> **模型虽然看到了历史，但训练目标没有逼它对跨轮状态和连续策略负责。**

所以真正有效的优化方向是：

> **从单步接话 SFT，升级到多步连续行为 SFT。**

这会比继续沿着“固定 16 轮 + 最后短 label”那条路加数据，更值得做。
