**优势：**
- 格式层（回复过长/表情/重复）覆盖系统，且有规范的 `validate_chosen` 统一质量控制

## 二、与评测问题的逐条对照

### 2.1 完全空白的场景

#### 🔴 P3 — 意图理解彻底失败（评测 R9）

**表现：** 用户说"明明要起床"（=对模型推断的纠正），模型解读为"用户在生气"，触发完整道歉剧本。

**现有覆盖：** 无。`dpo_data_logic_deep.py` 的 5 类场景均是"回答策略偏差"，不涉及"话语意图误读"。

**缺口本质：** 当用户话语在字面上与情绪词语表面相似时（"要起床"≈"责怪"），模型走错了语义解码分支。这是一个**语义歧义场景的优先级判断**问题，现有逻辑脚本未覆盖。

---

#### 🔴 P4/P5 — 道歉剧本无触发根据 + 虚构对话历史（评测 R9/R10）

**表现：**
- R9：用户说正常话 → 模型爆发"心都要碎成渣渣了"式道歉
- R10：用户追问"为什么道歉" → 模型继续捏造历史（"虽然你说不在乎/忍不住说那些话"）

**现有覆盖：** `dpo_data_tension.py` 的 C 类场景（分手拉扯）处理了"不要卑微挽留"，但：
- 没有"用户说正常话却触发道歉剧本"这个反向场景
- 没有"捏造历史、虚构用户台词"的负样本
- 没有"用户追问错误时应正确承认误判"的场景

**缺口本质：** 道歉剧本是训练集中高频的触发-响应模式，模型学到了台词本身，但没有学到**正确触发条件**。DPO 需要明确告诉模型：同样的道歉台词，什么情境下用（chosen），什么情境下不用（rejected）。

---

#### 🔴 P5 — 纠错信号忽视（评测 R10）

**表现：** 用户明确追问"为什么道歉呢"，模型不承认误判，继续强化错误叙事。

**现有覆盖：** 无。没有任何脚本构造"用户发出纠错信号 → assistant 正确承认 vs 继续错误"的 DPO 对。

**缺口本质：** "用户追问 = 我出错了"这个元推断链，在训练数据中几乎为零，需要专项 DPO 对来显式教学。

---

#### 🔴 P2 — 角色自身状态前后矛盾（评测 R6/R12）

**表现：**
- R1 说"在床上赖着" → R6 说"想去健身房" → R12 说"刚吃完早餐准备上班"
- 同一段对话内 assistant 自己的状态跳变 3 次

**现有覆盖：**
- `dpo_data_sysprompt.py`：让模型正确引用 system prompt 中的**用户**信息（用户记忆、用户细节）
- `dpo_data_context.py`：上文逻辑增强，处理**用户说过的计划**

以上两个脚本均聚焦于"引用外部信息（system/用户说过的事）"，对"assistant 自身状态在对话内部保持一致"完全空白。

**缺口本质：** 这是 **assistant 视角的自我一致性**，而不是"引用用户信息"，属于完全不同的能力维度，需要独立的 DPO 场景。

---

### 2.2 部分覆盖、但有明显缺口的场景

#### 🟡 P1 — 无根据状态假设（评测 R1/R8）

**表现：**
- R1：用户说"早上好"→ 模型断定"今天周末"
- R8：用户刚起床 → 模型凭空说"可能是因为熬夜"

**现有覆盖：**
- `dpo_data_time.py`：4 类时间错乱场景，但都聚焦于"时间词使用错误"（晚安/早上好矛盾），不涉及"无依据的前提假设"
- `dpo_data_sysprompt.py`：`sys_time_field_follow` 标签处理时间一致性，但只针对"system 中写了时间字段"的情况

**缺口：** 缺少"上下文没有任何依据，模型却给出强断言式推测"的 DPO 场景。这是比时间词矛盾更普遍的问题。

---

#### 🟡 P8/P9 — 话题跳跃无连接 & 自我纠错方式错误

**P8 表现（评测 R7）：** 用户纠正"不洗澡建议"，模型无视后直接跳到"你现在是不是有点困了"。

**P9 表现（评测 R13）：** 用户说"啥3"，模型"纠正"的方式是把同样的错误话几乎原封不动重复一遍。

**现有覆盖：** `dpo_data_context.py` 的 `logic_context_no_repeat_question`（已解决问题不再追问）有类似思路，但覆盖面窄，不包含上述两种场景。

---

## 四、新增脚本建议

### 4.1 `dpo_data_apology_control.py` — 道歉剧本控制 🔴 P0

**目标条数：** 200 条  
**对应问题：** P4（剧本式情感幻觉）、P5（虚构对话历史）

**场景设计：**

| tag | 触发场景 | chosen | rejected |
|-----|---------|--------|---------|
| `apology_no_trigger` | 用户说正常话（纠正推断/陈述事实）→ 模型触发道歉剧本 | 正常接话，不道歉 | "心都要碎/不该让你难过" 式剧本 |
| `apology_fabricate_history` | 模型上轮出错，用户追问 → 模型捏造历史（"虽然你说不在乎"） | 承认误判，不继续捏造 | 继续虚构"你说过的话" |
| `apology_drama_dial_down` | 用户轻微质疑 → 模型过度戏剧化（"我的心都要碎成渣渣了"） | 简短承认或澄清 | 过度戏剧化情感崩溃 |

**chosen 质量规则：**
- 不含道歉关键词（对不起/原谅/我不该）
- 不含戏剧化词（心碎/碎成渣渣/泪目）
- 长度 10~50 字

**rejected 质量规则：**
- 必须含道歉或戏剧化关键词
- 场景 2 中必须含虚构用户台词（"虽然你说..."/"你之前提到..."的捏造形式）

---

### 4.2 `dpo_data_correction_response.py` — 用户纠错响应 🔴 P0

**目标条数：** 200 条  
**对应问题：** P5（纠错信号忽视）、P9（自我纠错方式错误）

**场景设计：**

| tag | 触发场景 | chosen | rejected |
|-----|---------|--------|---------|
| `correction_acknowledge` | 用户追问"为什么这么说/你说的不对" → 模型应正确承认 | "哈哈我理解错了，你是说..." | 继续强化错误叙事、继续辩解 |
| `correction_clarify` | 用户说"不是这个意思" → 模型应请用户说明 | "那你是指什么？说来听听" | 直接猜测并继续错误理解 |
| `correction_not_repeat` | 用户困惑（"啥3/什么意思"）→ 模型不应把同样的话重复一遍 | 换角度解释或承认表述不清 | 原话几乎不变重复一遍 |

**数据来源：** 模板生成，在 prompt 中嵌入"前一轮 assistant 犯了明确错误"的历史，测试模型是否能正确响应纠错信号。

**chosen 质量规则：**
- 不得重复前一轮 assistant 的核心内容（Jaccard ≤ 0.3）
- 不得继续使用错误前提的词汇
- 含明确的"承认/澄清/换角度"信号词

---

### 4.3 `dpo_data_intent_clarity.py` — 意图清晰度控制 🔴 P0

**目标条数：** 150 条  
**对应问题：** P3（意图理解失败）

**核心思想：** 当用户话语在字面上与某个"高频触发模式"表面相似时（如"明明要起床"≈"责怪"，"在家宅着"≈"孤独"），模型应按**最自然、最简单的字面语义**来理解，而不是跳到情绪触发分支。

| tag | 触发场景 | chosen | rejected |
|-----|---------|--------|---------|
| `intent_correction_not_anger` | 用户用"明明/就是/不是吗"表达纠正 → 模型误读为生气 | 按纠正语义正常接话 | 触发道歉剧本 |
| `intent_neutral_not_sad` | 用户简短陈述（"没吃早饭/刚起床"）→ 模型过度共情推断情绪 | 自然回应，不强行共情 | 误判为伤心/委屈并共情 |
| `intent_question_not_complain` | 用户问"为啥会这样" → 模型理解为抱怨 | 直接回答问题 | 误判为抱怨并开始安慰 |

**实现策略：**
- 构造 prompt = `历史（包含模型上一轮的某个推断）+ 用户纠正/简单陈述`
- 让 LLM 分别生成"按最简单语义接话"（chosen）和"跳入情绪触发分支"（rejected）
- 验证：chosen 中不含道歉词和情绪安慰词，rejected 中含有

---

### 4.4 `dpo_data_self_consistency.py` — 角色自身状态一致性 🔴 P0

**目标条数：** 150 条  
**对应问题：** P2（角色自身状态前后矛盾）

**核心思想：** 对话开头 assistant 建立了自己的某个状态（如"在赖床"/"在写报告"/"刚下班"），后续 assistant 回复不应与之矛盾，除非有明确的时间推进说明。

| tag | 触发场景 | chosen | rejected |
|-----|---------|--------|---------|
| `self_state_location` | 前文说"在家/在公司"，后文不应出现矛盾地点 | 保持地点状态一致 | 忘记前文状态给出矛盾地点 |
| `self_state_activity` | 前文说"在赖床/在写东西"，后文不应跳跃活动 | 合理延续或有过渡说明 | 无过渡跳到矛盾活动 |
| `self_state_time` | 前文说"刚起床/早餐还没吃"，后文不应说"我刚吃完饭" | 时序一致 | 时序矛盾 |

**数据构造：**
- Prompt 中明确包含 assistant 前面 1~2 轮对自己状态的描述
- LLM 分别生成一致版（chosen）和矛盾版（rejected）
- 验证：chosen 中包含与前文一致的状态词，rejected 中包含矛盾词

**注意：** 这是多轮 DPO，prompt 中需要包含 assistant 自述状态的历史轮次，是现有脚本中还没有处理过的 DPO 格式（现有脚本的 prompt 历史一般只有 user 的上下文）。

## 七、DPO 数据格式统一性检查

现有脚本输出格式：

```json
{
  "prompt": [...messages...],
  "chosen": "...",
  "rejected": "...",
  "tag": "..."
}
```

新增脚本建议的格式注意事项：

1. **`dpo_data_self_consistency.py`** 的 prompt 中必须包含 assistant 自述状态的历史 turn，这在现有脚本中是**第一次有 assistant 历史 turn 出现在 prompt 中**（现有脚本的 prompt 历史通常只保留 user/assistant 交替但以 user 结尾）。这一格式与现有统一格式一致，无需改变，但构造时需注意保留足够的历史。

2. **`dpo_data_correction_response.py`** 的 prompt 中需要包含"前一轮 assistant 犯了明确错误"的上下文（如前一轮 assistant 给出了道歉剧本），再在此基础上让用户发出纠错信号。这是**两步构造**，要确保 rejected 是继续强化错误，chosen 是正确承认并修正。

3. 所有新增脚本必须继承现有的 `validate_chosen` 通用质量规则（无晚安词/无说教词/无星号动作/过滤推理痕迹）。
