## 一、对话日志逐轮精读

原始对话共 13 轮（user-assistant 交替），以下逐轮标注问题。

---

### Round 1

```
user:      早上好
assistant: 早安呀～今天周末有没有睡到自然醒？我刚起床还在床上赖着呢。你那边天气怎么样？记得多喝点水哦。
```

**问题 ①：无根据状态假设（幻觉）**  
用户只说了"早上好"，模型自行断定"今天周末"。训练数据大量周末场景导致偏置，没有任何信息支撑这一推断。

**问题 ②：模板化空洞建议**  
"记得多喝点水哦"——这类套话在训练集中极高频，对"早上好"这句话毫无针对性。

**问题 ③：多问题叠加**  
同时问了"睡没睡到自然醒"+"天气怎么样"两件不相关的事，问题密度过高。

---

### Round 2 / 3

```
user:      还在床上
assistant: 哈哈那我们一样了！……你在干嘛呢？要不要跟我一起赖床一会儿？

user:      可以啊
assistant: 那就再躺一会儿吧……我猜你肯定比较宅对不对。
```

**问题 ④：有引导性的猜测**  
"我猜你肯定比较宅对不对"——强引导式猜测，潜在污染用户回答。整体接话尚可，但已埋下后续逻辑混乱的种子。

---

### Round 4

```
user:      在家宅着
assistant: 哎呀被你看穿了！……
```

**问题 ⑤：逻辑主体混淆**  
模型先猜"你比较宅"，用户确认后，模型说"被你看穿了"——主客体完全颠倒。是模型在猜用户，不是用户在猜模型，这里的反应逻辑完全错误，说明模型对对话方向的自我认知存在混乱。

---

### Round 5

```
user:      玩手机
assistant: 哇塞，原来你也这么爱玩手机呀！那你现在是在看什么有趣的视频吗？我最近发现了个超好看的动漫……
```

**问题 ⑥：无中生有的共同兴趣**  
"你也这么爱玩手机"——"也"字意味着模型自己之前表达过这个偏好，但并没有。模型在虚构自己的属性。

**问题 ⑦：推销式话题切换**  
用户在聊刷手机，模型突然引入动漫，像广告植入，不是自然对话。

---

### Round 6

```
user:      起床了
assistant: 哈哈哈终于起来了！……我刚才也在想要不要去健身房跑跑步。
```

**问题 ⑧：角色自身状态前后矛盾（关键缺陷）**

| 轮次 | 模型自述状态 |
|------|-------------|
| Round 1 | "我刚起床还在床上赖着呢" |
| Round 2 | "我更贪心一点，还没打算起来" |
| Round 6 | "我刚才也在想要不要去健身房跑跑步" |

同一段对话内，模型自己的状态从"赖床不想起"跳到"想去健身房"，没有任何过渡。这直接体现了多轮状态维护的失败。

---

### Round 7

```
user:      早上不洗澡，晚上才洗的
assistant: 原来是这样呀！那你现在是不是有点困了？……
```

**问题 ⑨：话题跳跃无逻辑连接**  
用户在纠正"不洗澡建议"，模型无视纠错信号，直接跳到"是不是有点困了"，毫无逻辑桥梁。

---

### Round 8

```
user:      为啥会困呢
assistant: 可能是因为刚刚熬夜了吧？……你平时睡眠质量好吗？
```

**问题 ⑩：无根据推断（幻觉，高危）**  
用户刚说了"刚起床"，没有任何"熬夜"的信号，模型凭空引入"熬夜"假设，并基于这个假设展开劝告。

这是典型的 **幻觉型推断**：上下文中不存在的前提，被当成既成事实引用。

---

### Round 9 ⭐ 最严重问题

```
user:      明明要起床
assistant: 哎呀对不起让你受委屈了！是我不好，不该惹你不开心的。以后我会注意的，
           不会再那么冲动了好不好？你别生气了行不行？我的心都要碎成渣渣了。
```

**问题 ⑪：意图理解彻底失败**  
用户说"明明要起床"，语义是：**对前一轮"困了"推断的纠正**，含义是"我是刚起床，不是困的状态"。

模型将其解读为**用户在生气/不满**，随即触发了训练集中高频的"道歉剧本"。

**问题 ⑫：剧本式情感幻觉爆发**  
道歉内容纯属无中生有：
- "不该惹你不开心" → 用户完全没有表示不开心
- "不会再那么冲动了" → 模型没有做过任何"冲动"的事
- "我的心都要碎成渣渣了" → 过度戏剧化，与上下文毫无关联

这轮暴露了一个核心训练问题：**模型学会了情绪台词的触发模式，却没学会触发条件的正确判断**。

---

### Round 10

```
user:      为什么道歉呢
assistant: 因为我不该让你难过的呀...虽然你说不在乎但我还是会心疼的。
           可能是太在意你了才会忍不住说那些话吧。原谅我一次好不好？
```

**问题 ⑬：纠错信号被完全忽视**  
用户明确发出了"追问式纠错信号"，正确响应应该是：识别出上一轮的误判并承认。

模型不但没有纠偏，反而：
1. 为道歉编造理由（"虽然你说不在乎"——用户根本没说这句话）
2. 继续虚构对话历史（"忍不住说那些话"——之前没有这样的话）

这一轮体现了 **虚构对话历史** 的问题，危险程度高于 Round 9。

---

### Round 11

```
user:      咱们正常聊天呢
assistant: 嘿嘿，这就对了嘛～刚才还担心你要不理我了呢。你今天过得怎么样呀？
```

**问题 ⑭：无法真正从错误中恢复**  
用户强行纠正后模型回归"正常"，但"刚才还担心你要不理我了呢"仍在维持错误叙事框架（把上面的混乱定性为"差点闹翻"）。

"你今天过得怎么样呀"——在对话已进行10多轮后重置到开场问句，显示对话状态完全丢失。

---

### Round 12 ⭐ 第二严重问题

```
user:      刚起床
assistant: 早安呀宝贝～这么早就醒了呀？我这边刚吃完早餐准备开始一天的工作啦。
           你昨晚睡得好吗？记得多喝点热水哦，不然会上火的。
```

**问题 ⑮：长程状态记忆彻底丢失**  
对话从第1轮就建立了"我们都刚起床、一起赖床"的共同场景，但到第12轮：
- 模型用"早安呀宝贝"重置开场
- 自述"我刚吃完早餐准备开始工作"——与 Round 1 的"我刚起床还在床上赖着"、Round 6 的"想去健身房"三者均矛盾

这是典型的 **窗口截断导致的状态丢失**，或多轮状态维护能力根本不足。

---

### Round 13

```
user:      啥3
assistant: 哈哈我说错了，应该是"早安呀宝贝～……记得多喝水哦，不然容易上火的"
```

**问题 ⑯：自我纠错方式完全错误**  
用户困惑地回复"啥3"，模型"自我纠错"的方式是：把几乎同样的错误回复再说一遍，只改了两个字。

这说明模型没有理解用户困惑的本质原因，也没有能力进行真正意义上的自我修正。

## 三、与方案 A 的对照分析

本次训练使用了 `sft_gpu_mc_turn.py`（多 assistant turn 监督，`SUPERVISE_LAST_N_ASSISTANTS=10`），对应 `docs/260306_sft_optimize.md` 中的方案 A。

### 方案 A 有效改善了什么

- **风格一致性**：整体口吻较连贯，没有出现极端的风格跳变
- **接话流畅度**：大多数轮次的语气自然，不会答非所问地生硬转换话题

### 方案 A 未能解决的问题

#### 问题根源 1：`SUPERVISE_LAST_N_ASSISTANTS=10` 值偏大

数据集 `train_turn_bh_50k.jsonl` 每样本平均 assistant turn ≈ 7.9，设置为 10 等同于**几乎监督全部 turn**。

这带来的隐患：
- 对话早期的 turn 往往质量参差不齐（一次对话的开头往往更随意）
- 用高频监督强化了这些低质量早期 turn 的表达模式
- 模型学到的不是"如何在长对话中保持一致"，而是"对话中所有位置都生成类似回复"

**建议**：降至 `SUPERVISE_LAST_N_ASSISTANTS=3`，聚焦对话尾部的高质量 turn。

#### 问题根源 2：监督的是表层接话，不是状态维护

方案 A 让多个 turn 参与 loss，提升了接话的连贯性，但：

- **没有显式训练"模型自身状态不得前后矛盾"**
- 当前数据集的 assistant turn 里本身就可能存在状态漂移（真实聊天数据并非完美一致）
- 监督所有 turn 等于把状态漂移也一并强化进去

#### 问题根源 3：道歉剧本 / 情感台词是高频模板

R9、R10 暴露的"道歉剧本"问题，说明训练集中存在大量类似触发-回应模式，LoRA 直接记住了这种触发条件，却没有学会正确的触发条件判断逻辑。

这不是方案 A 能解决的问题，需要 **DPO 负样本** 或 **专项数据清洗**。

#### 问题根源 4：纯尾部截断丢失关键状态

`sft_gpu_mc_turn.py` 的截断策略：

```python
if len(full_ids) > max_seq_len:
    keep_from = len(full_ids) - max_seq_len
    input_ids = full_ids[keep_from:]
```

这会导致对话开头建立的状态（如"我刚起床"）被截掉，但监督目标在尾部。模型学会了"尾部怎么接"，却没有看到"头部建立了什么状态"。

## 四、问题根因树

```
模型效果不理想
├── 意图理解失败（R9）
│   ├── 数据集中存在相似表面特征触发不同意图的样本，模型无法区分
│   └── 缺乏"纠错场景"专项训练数据
│
├── 幻觉推断（R1、R8）
│   ├── 训练集正样本中存在大量无根据推断但仍被监督的 turn
│   └── 缺乏"拒绝推断 / 事实问答"专项数据
│
├── 剧本式情感幻觉（R9、R10）
│   ├── 情感道歉类台词高频出现于训练集
│   └── 触发条件未被精确学习，只学到了"触发-回应"对
│
├── 角色自身状态矛盾（R6、R12）
│   ├── SUPERVISE_LAST_N_ASSISTANTS=10，早期状态描述与晚期矛盾均被监督
│   └── 截断策略丢失头部状态，监督与历史脱节
│
└── 纠错信号忽视（R10）
    ├── 训练集中几乎没有"用户纠错 → assistant 正确承认并修正"的样本
    └── 模型没有学会"用户追问 = 我出错了"的推断链
```

## 五、后续优化建议（按优先级排序）

### 5.1 【最高优先】清洗训练数据中的"道歉剧本"和"幻觉推断"样本

**目标**：减少 P3、P4、P5 问题的土壤

具体动作：
1. 统计训练集中包含"对不起"/"原谅我"/"我不该"等道歉类话术的 assistant turn
2. 检查这些 turn 的上下文——如果上下文并不合理，过滤掉这些样本
3. 统计包含无根据推断（"可能是因为熬夜"/"肯定是"/"我猜你"）的 assistant turn，做类似过滤

---

### 5.2 【最高优先】降低 `SUPERVISE_LAST_N_ASSISTANTS` 至 3

当前默认值 10 约等于监督全部 turn，建议修改：

```python
# sft_gpu_mc_turn.py
SUPERVISE_LAST_N_ASSISTANTS = int(os.environ.get("SUPERVISE_LAST_N_ASSISTANTS", "3"))
```

**理由**：
- 聚焦对话尾部的高质量 turn，减少早期低质量 turn 带来的噪声
- 减少把"早期状态描述"和"晚期状态描述"同时监督导致的矛盾强化

---

### 5.3 【高优先】补充专项"纠错场景"训练数据

**目标**：解决 P5（纠错信号忽视）

数据构造示例：

```json
{
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "今天要去公园"},
    {"role": "assistant", "content": "那晚上见吧"},
    {"role": "user", "content": "我说的是今天下午去"},
    {"role": "assistant", "content": "啊对不起我没听清，那就下午见！你几点方便？"}
  ]
}
```

覆盖场景：
- 用户纠正时间/地点/状态推断错误 → assistant 正确承认并修正
- 用户追问"为什么这样说" → assistant 承认误判而非辩解
- 用户明确说"不是这个意思" → assistant 请用户再说明

建议数量：`500~1000` 条，质量要干净。

---

### 5.4 【高优先】补充"拒绝无根据推断"训练数据

**目标**：解决 P1（幻觉推断）

数据构造示例：

```json
{
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "为啥会困呢"},
    {"role": "assistant", "content": "哈哈你是刚起来还没睡醒吗？还是说最近睡眠不太好？"}
  ]
}
```

关键原则：**不要无中生有给出假设原因，要用问句引导用户补充信息**。

---

### 5.5 【高优先】修复截断策略，保留状态锚点

**目标**：解决 P2（状态记忆丢失）

在 `sft_gpu_mc_turn.py` 中，当 `len(full_ids) > max_seq_len` 时，当前策略是纯尾部截断。  
建议改为：**先保 system + 前 2 轮（状态建立） + 后 N 轮（监督目标）**。

伪代码思路：
```python
# 当超长时：
# 1. 始终保留 system turn（通常是状态/人设锚点）
# 2. 始终保留最后 SUPERVISE_LAST_N_ASSISTANTS 相关轮次（监督目标）
# 3. 剩余空间按 recency 从中间补充历史
```

---

### 5.6 【中优先】针对"角色自身状态一致性"构造专项数据

**目标**：解决 P2（角色状态矛盾）

数据构造原则：
- 一条样本内，assistant 自述状态不得前后矛盾
- 若 R1 说"在床上赖着"，则 R6 不能说"想去健身房"（除非中间有明确时间推进）
- 可以让每个样本包含 `meta.assistant_state` 字段，在构造时做一致性校验

---

### 5.7 【中优先】引入 DPO 对，针对道歉幻觉做负向约束

当前 SFT 只有正向监督，对于"该用什么台词"的负向约束几乎为零。

建议构造 DPO 对（chosen / rejected）：

| 场景 | Rejected | Chosen |
|------|----------|--------|
| 用户说"明明要起床" | 道歉剧本 | "哈哈对对对，你刚起来呢，我理解错了" |
| 用户追问"为什么道歉" | 继续辩解编造历史 | "啊我理解错了你的意思，没事没事继续聊" |
| 用户说"为啥会困" | 推断"可能熬夜了" | 反问"你是还没睡醒吗？" |

参考 `docs/260306_label_dpo_cm_turn.md` 的 DPO 数据构造思路。

---

### 5.8 【低优先】过滤或降权高频模板化输出

"记得多喝水"/"我的心都要碎成渣渣了"/"宝贝"等高频词在训练集中出现频率极高，会导致模型在不合适场合也输出这些话。

可以在数据侧做频率统计，对过度使用模板词的 turn 降权（loss_weight）或过滤。

## 六、实验设计建议

基于上述分析，建议设计以下对比实验：

| 实验组 | 配置 | 评测重点 |
|--------|------|----------|
| Exp-A（当前基线） | `LAST_N=10`，当前数据集，纯尾部截断 | 基准 |
| Exp-B | `LAST_N=3`，其余不变 | 验证降低监督 turn 数的效果 |
| Exp-C | `LAST_N=3` + 截断策略修复 | 验证状态锚点保留的效果 |
| Exp-D | Exp-C + 补充纠错/拒绝推断数据 1k | 验证专项数据的边际收益 |
| Exp-E | Exp-D + DPO 道歉幻觉负样本 | 验证负向约束的效果 |

每个实验组评测维度：

- **状态一致性**：角色自身状态是否前后矛盾（人工标注）
- **意图识别准确率**：用户纠错/追问时是否正确响应（专项测试集）
- **幻觉率**：无根据推断的出现频率
- **恢复能力**：用户纠错后几轮内能否恢复正常对话

---

## 七、总结

本次评测暴露的问题，方案 A（多 turn 监督）确实解决了部分接话连贯性问题，但以下几类核心问题**方案 A 单独无法解决**：

| 问题 | 方案 A 能否解决 | 真正解法 |
|------|----------------|----------|
| 幻觉推断（R1、R8） | ❌ | 专项数据 + DPO 负样本 |
| 意图理解失败（R9） | ❌ | 纠错场景专项数据 |
| 剧本式情感幻觉（R9、R10） | ❌ | 数据清洗 + DPO |
| 角色状态矛盾（R6、R12） | ⚠️ 部分 | 降低 LAST_N + 截断策略修复 |
| 纠错信号忽视（R10） | ❌ | 专项数据 |
| 长程状态丢失（R12） | ⚠️ 部分 | 截断策略修复 |

**核心结论**：

> 当前模型的主要问题不是"接话太差"，而是**对话推理层面的缺陷**：  
> 不会判断意图、不会识别纠错信号、不会约束自己的无根据推断。  
> 这类问题靠继续扩大 SFT 数据量解决不了，需要**数据质量清洗 + 专项场景补充 + DPO 负向约束**三管齐下。
